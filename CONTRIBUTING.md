# Contributing to BoardKit

This guide covers how the repository is set up, how to propose a change, and the standards a change is reviewed against.

BoardKit is a pnpm monorepo. Three packages are published to npm:

| Package | Path | What it is |
|---|---|---|
| `@onioneko/boardkit-core` | `packages/core` | The engine: parse, link, validate, resolve, project, write, events, ports |
| `@onioneko/boardkit-html` | `packages/html` | The `html` projector |
| `@onioneko/boardkit-blocks` | `packages/blocks` | Six ready-made block types |

Two workspace packages are private and never published: `apps/demo` (`boardkit-demo`, a local workbench server) and `examples/` (`boardkit-examples`, runnable scripts that CI checks). User documentation lives in `docs/`. `docs/api` is generated by typedoc.

Bug fixes, tests, documentation improvements and new features are all welcome. For anything larger than a small fix, open an issue first (see [Proposing a change](#proposing-a-change)).

## Setup

You need Node 22 or newer (`.nvmrc` pins 24; CI tests 22 and 24; `engine-strict` rejects older versions) and pnpm via Corepack (`corepack enable`; `packageManager` pins the version).

Install and build:

```bash
corepack enable
pnpm install
pnpm build
```

Build before you run anything else. Each package resolves the other workspace packages through their `package.json` `exports`, which point at the built `dist/` output. Until `pnpm build` has run, `pnpm typecheck` and `pnpm test` fail in `packages/html`, `packages/blocks`, `apps/demo` and `examples` because they cannot find `@onioneko/boardkit-core`. Rebuild after you change a package that others depend on.

## Everyday commands

All commands run from the repository root.

| Command | What it does |
|---|---|
| `pnpm build` | Builds every workspace package (`tsc -p tsconfig.build.json`) into its `dist/` |
| `pnpm typecheck` | Type-checks every workspace package, including tests (`tsc --noEmit`) |
| `pnpm test` | Runs every package's vitest suite once |
| `pnpm lint` | Runs `biome check .`: lint rules, formatting and import sorting |
| `pnpm format` | Rewrites files with the biome formatter |
| `pnpm example <file>` | Runs one script from `examples/`, for example `pnpm example 01-hello.ts` |
| `pnpm changeset` | Adds a changeset (see [Changesets](#changesets)) |
| `pnpm docs:api` | Regenerates the API reference in `docs/api` |

To work on one package, filter by its name:

```bash
pnpm --filter @onioneko/boardkit-core test
pnpm --filter @onioneko/boardkit-core typecheck
pnpm --filter @onioneko/boardkit-core test:watch
```

`test:watch` exists in `packages/core` and `packages/html`. To start the workbench, run `pnpm --filter boardkit-demo demo`. The [README](README.md#try-it-the-workbench) explains what it does.

`biome.json` does not exclude build output, so after a build `pnpm lint` also reports findings in `dist/` directories. Those are not part of your change. CI lints a fresh checkout, before it builds.

## Proposing a change

1. **Open an issue first** for a new feature, a public API change, a new dependency, or anything that touches more than one package. Describe the problem and the behavior you propose. Agreeing on the behavior before you write code saves both sides a rewrite. Small fixes and documentation corrections can go straight to a pull request.
2. **Fork the repository and create a branch** from `main`.
3. **Make the change test-first** (see [Test-first process](#test-first-process)) and keep it focused on one concern.
4. **Add a changeset** if the change affects a published package (see [Changesets](#changesets)).
5. **Run the same checks as CI**, in this order:

   ```bash
   pnpm install --frozen-lockfile
   pnpm lint
   pnpm build
   pnpm typecheck
   pnpm test
   ```

   CI (`.github/workflows/ci.yml`) runs lint (`pnpm exec biome ci .`, the read-only form of `pnpm lint`), typecheck, build and test on Node 22 and 24, on every push and pull request.

6. **Open a pull request** against `main`. Say what changed and why, link the issue, and list anything you could not verify.

### What reviewers look for

- The checks above pass.
- The change stays in scope: no unrelated refactors, renames or formatting churn.
- A public API change is documented in JSDoc and has a changeset.

### Commit messages

The format is not enforced, but please use `type(scope): summary`, for example `feat(core): add value-CAS rebase to patch writes`, `fix(html): keep checklist inputs enabled`, `test(parse): cover empty frontmatter`, or `docs: fix the sources guide example`. The scope is a package or a module when one applies.

## Test-first process

Every change follows red, green, refactor:

1. **Red.** Write a failing test first. Tests are colocated with the module they cover, as `*.test.ts` next to the source file. Each behavior gets at least one test. Run it and watch it fail for the reason you expect.
2. **Green.** Write the minimal implementation that makes the test pass.
3. **Refactor.** Improve the code while the tests stay green.

Test conventions in this repository:

- **Golden fixtures.** Parse and projection tests read Markdown fixtures from `packages/core/test/fixtures/` and `packages/html/test/fixtures/`. `fin.md` is the canonical example document.
- **Storage.** Tests that need storage use `createMemStorage()`, the in-memory adapter backed by a memfs volume. Tests of the filesystem adapter use a temporary directory.
- **Time.** Code never reads the system clock directly, so tests pass a fixed `Clock`.
- **Public surface.** Integration tests import only from the package's `src/index.ts`. Unit tests may import internal modules.
- **Nothing test-only ships.** Each package publishes its `src/` next to `dist/` so source maps resolve, minus `*.test.ts` files and `__fixtures__` directories. Keep test helpers and fixtures in `test/`, in a `*.test.ts` file or under `src/**/__fixtures__/`, never as an ordinary module in `src/`.

There is no numeric coverage threshold, but every exported symbol is touched by at least one test.

If the intended behavior of a case is unclear, do not guess. Ask in the issue or the pull request, and leave the case out of the change until it is settled.

## Coding standards

The standards come in four parts: TypeScript rules that reviewers check, compiler settings that the shared tsconfig enforces, BoardKit-specific conventions, and architecture rules.

### TypeScript rules

These follow the [Google TypeScript Style Guide](https://google.github.io/styleguide/tsguide.html), trimmed for an ESM-only library.

| # | Rule |
|---|---|
| 1 | All code is TypeScript under `strict: true`. No `any`: biome reports `noExplicitAny` as an error. Use `unknown` and narrow it. |
| 2 | Exported functions declare explicit return types. This keeps the public API contract visible and speeds up compilation. |
| 3 | Model state with discriminated unions (for example `DocNode`). Do not use TS `enum`: use literal unions and `satisfies`. |
| 4 | Prefer `undefined` to `null`: an absent field means "not present". Use `null` only when the distinction matters, and document it. |
| 5 | Naming: camelCase for variables and functions, PascalCase for types, interfaces and classes, UPPER_SNAKE_CASE for true constants, kebab-case for file names. |
| 6 | Formatting is biome's: 2-space indent, 100-column lines, double quotes, semicolons, trailing commas. Always use braces. |
| 7 | Use arrow functions for anonymous callbacks and `function` declarations at the top level. |
| 8 | No `namespace` and no `var`. Use `const` and `let`. Import types with `import type` (`verbatimModuleSyntax` enforces it). |
| 9 | Use strict equality (`===`). Do not use `!!`: use `Boolean()` or an explicit comparison. |
| 10 | Use template literals instead of string concatenation. |
| 11 | Every exported symbol carries JSDoc. The API reference is generated from it. |
| 12 | Programming errors throw an `Error` instance, a subclass where callers need to tell failures apart, and never a string. Expected failures do not throw (see B4). |
| 13 | Exported data structures are `readonly` by default. Never export a mutable singleton. |
| 14 | Prefer `Array.isArray`, `Object.hasOwn`, optional chaining and nullish coalescing. |

### Compiler settings

`tsconfig.base.json` sets these for every package. Do not override them in a package tsconfig.

- `strict`
- `noUncheckedIndexedAccess`
- `exactOptionalPropertyTypes`
- `verbatimModuleSyntax`
- `erasableSyntaxOnly`
- `isolatedModules`
- `module` and `moduleResolution`: `NodeNext`
- `target`: `ES2023`

### BoardKit conventions

Source comments refer to these by their labels (for example "CONTRIBUTING B6").

| # | Convention |
|---|---|
| B1 | **ESM only.** Named exports only, no default exports. This keeps refactors and tree-shaking simple. |
| B2 | **NodeNext imports.** Relative imports carry the `.js` suffix: `import { X } from "./model/doc.js";`. |
| B3 | **Branded identifiers.** `DocId`, `SectionId`, `BlockId` and version strings are branded types. A bare `string` does not cross those boundaries. |
| B4 | **Diagnostics, not exceptions.** Expected failures never throw. Parse and validate failures return `Diagnostic[]` with a `code`, a `message` and a position; other expected failures return result objects. Failures stay local: one bad document, reference or block degrades only itself, never the whole projection. |
| B5 | **Purity.** Pure modules under `src/` have no side effects: no `Date.now`, no `Math.random`, no IO. Time flows through the `Clock` port and IO through the other ports. |
| B6 | **The public API is `src/index.ts`.** Anything not exported there is internal. `@onioneko/boardkit-core/internal` exposes pipeline internals with no stability guarantee. |
| B7 | **Correctness first.** Avoid needless allocation in the parse and link hot paths, but do not optimize without a benchmark that shows the need. |
| B8 | **Determinism.** The same inputs give the same outputs. Order-sensitive collections are sorted explicitly. |

### Architecture

- The library provides mechanism and the host provides meaning. `core` behavior code carries no domain semantics (LLMs, agents, finance, and so on). The engine is writer-agnostic and consumer-agnostic by construction.
- Each module in `packages/core/src` has one responsibility (see the module map in [AGENTS.md](AGENTS.md#module-map)). Keep new behavior in the module that owns it.
- `@onioneko/boardkit-core` never depends on the other packages. `@onioneko/boardkit-html` and `@onioneko/boardkit-blocks` depend only on core at runtime and never on each other.
- Shared dependency versions are declared once, in the pnpm catalog in `pnpm-workspace.yaml`. Packages refer to them as `catalog:`. Justify any new dependency in the pull request.

## Changesets

Releases are driven by [changesets](https://github.com/changesets/changesets). If your change affects what users of a published package see (behavior, API, types, or a bug they could hit), add a changeset:

```bash
pnpm changeset
```

The command asks which packages changed and which bump each one needs, then writes a Markdown file to `.changeset/`. Commit that file with your change. Changes that touch only tests, internal tooling, `docs/`, `apps/demo` or `examples/` do not need one.

**Picking a bump.** The packages are pre-1.0 (`0.x`), so:

- `patch`: a bug fix or an internal change with no API change.
- `minor`: a new feature, or any breaking change to the public API.
- `major`: held back until 1.0.

**Writing the entry.** Write for someone upgrading the package. Say what changed in user-visible terms, name the affected API, and tell them what to do if they must change their code. One sentence is enough for a fix. For a breaking change, list each change as its own bullet. For example:

```markdown
---
"@onioneko/boardkit-html": patch
---

Block-hook `<input>` elements are no longer forced `disabled` by the sanitizer, so `data-intent` checkboxes are clickable.
```

## Releasing

You do not publish anything yourself. A release flows like this:

1. **A changeset in a pull request.** Your pull request adds a changeset (see [Changesets](#changesets)) and is merged into `main`.
2. **The version pull request.** On every push to `main`, the release workflow (`.github/workflows/release.yml`) runs the same checks as CI and collects the pending changesets into a "Version Packages" pull request that bumps the versions and updates the changelogs. Further changesets merged before it is released are added to the same pull request.
3. **Merging it publishes.** When a maintainer merges the version pull request, the workflow runs the checks again and publishes the new versions to npm from CI, through npm trusted publishing, with a provenance attestation linking each version to the workflow run that built it. It also creates the git tags and GitHub releases.

The three packages are versioned in lockstep: every release gives core, html and blocks the same version, whichever of them the changesets name.

The one-time setup behind this (npm trusted publishers and repository settings) is in [RELEASING.md](RELEASING.md).

## Reporting a security issue

Do not report a security vulnerability in a public issue. Report it privately through GitHub private vulnerability reporting, as described in [SECURITY.md](SECURITY.md), which also lists the supported versions and what to include.

The workflow opens the version pull request with a token from the `onioneko-boardkit-release` GitHub App rather than `GITHUB_TOKEN`. Pull requests created with `GITHUB_TOKEN` do not trigger workflows, so CI would not run on them and the ruleset on `main` would block the merge. The App needs only contents and pull-requests write access on this repository, plus two repository settings: the variable `RELEASE_APP_CLIENT_ID` and the secret `RELEASE_APP_PRIVATE_KEY`.
